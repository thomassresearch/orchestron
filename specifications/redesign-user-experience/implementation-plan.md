# Perform workspace implementation plan

**Proposed delivery sequence · 18 November 2026.** The goal is to let a musician arrange a song, launch pads and mix it in one browser window. Arrange keeps the timeline above the editor, Live keeps the keyboard available during launches, and Mix keeps Master and final output in sight. Each view resumes where the musician left it. The approved design and the silent study are the references for interaction and layout. [Interaction specification](layout-and-interaction-spec.md) · [Interactive study](orchestron-studio-study.html)

## Delivery sequence

| Milestone | Deliverable | Depends on | Ready to proceed when |
| --- | --- | --- | --- |
| 1. Establish the baseline | Reproducible clip-based and legacy workflows, identified state owners and baseline measurements | Current application | The team can reproduce a live launch, a scoped edit and a direct-output mix in the application. |
| 2. Separate navigation from editing | View memory, explicit edit targets, shared project dialogs | 1 | Switching views with a dirty clip cannot change its content or redirect a Live edit into it. |
| 3. Build the browser shell | Bounded working area, right Inspector, resizable dock, shared commands and status | 2 | Real controls fit at desktop and single-pane sizes. Navigation causes no transport or configuration calls. |
| 4. Move Arrange | Timeline, inspector properties and contextual editors running on existing actions | 2–3 | A musician can create the first track and edit one occurrence of a linked phrase during playback. |
| 5. Move Live | Device launcher, active keyboard, MIDI controls and explicit pad editing | 2–3 and the shared editors from 4 | A musician can hold a chord and launch two pads in succession on desktop and in a narrow window. |
| 6. Move Mix and rack controls | Mixer, routing, rack, instrument controls and sample maps | 2–3 | A musician can follow a direct-output signal, adjust an insert and return to the same clip. |
| 7. Verify and switch the entry point | Application browser tests, listening checks, localized help and English manual | 4–6 | Both performance formats pass the workflow and compatibility checks below. |

Build and review each milestone as a separate change. Exercise the new composition in a frontend browser harness while the current Perform entry point serves users. After parity is demonstrated, switch that entry point in one change that can be reverted independently. The existing clip-arranger compatibility switch keeps its current purpose throughout.

## 2. Give each view its own working context

**Implemented in the application preview on 18 November 2026.** Clip and legacy sessions passed the browser round trip. The running clip session also passed the transport and configuration checks. [Milestone 2 implementation and replay](milestone-2-view-state.md)

Use the retained editor store as the single owner of new presentation state. Represent the current Perform view and a separate entry for each view. Reuse device-, binding- and route-owned entries for the values that already have those lifetimes. Keep live references to drafts by target identity. Copying draft payloads into a view snapshot would allow a later return to resurrect stale edits.

| Owner | Values to retain |
| --- | --- |
| Each view | Right sidebar, narrow drawer, compact rack, dock open/closed, dock kind, expanded state, preferred split height, expanded property sections and scroll offsets for each visible region. |
| Arrange | Lane and clip IDs, nested occurrence path and repetition pass, current editor target and selection, timeline zoom and scroll, Fit tracks, and editor/Inspector positions. Preserve existing range, clipboard and history ownership. |
| Live | Selected device, its editing pad, editor or keyboard, launcher scroll and detail position. Keyboard routing, device enablement and live controller values continue to use their existing owners. |
| Mix | Mixer/Rack/Routing subview, selected binding or Master, control group, channel bank on both axes, Master scroll, routing disclosure and Inspector position. Use binding IDs so identical patches resolve to the correct instance. |
| Shared performance | Authored definitions and routing, pending drafts and intent, song position, engine ownership, device phase and queue, current meters and dirty state. Read these from their existing stores when a view appears. |

Implement a single navigation action for the view buttons, return from Instrument Design and contextual commands such as **Manage rack**. On departure, capture offsets from mounted regions, end gestures owned by the outgoing panel and apply its existing audition cleanup. On arrival, validate the saved identities, mount the destination, restore disclosures and split geometry, then apply offsets after layout and clamp to current bounds. A hidden or zero-sized region must keep its last usable offset. Keep focus on the activated view button for ordinary navigation. A repeat press leaves the active view in place.

Keep open drafts across navigation while activating only the edit target of the visible editor. Audit callers of `sequencerEditingView`, `openClipEditor` and `clipEditingKey`. Pass an explicit target or detach and rebind the active draft key when changing editors. Do this before a new editor can accept input. Verify that switching alone cannot allocate a musical edit, commit scope, start an audition, enqueue a pad, issue a seek, dirty the performance or schedule audio preparation. [Clip actions](../../frontend/src/store/clipActions.ts) · [Device edit routing](../../frontend/src/store/sequencerEdits.ts)

Host project-level draft resolution once where Save, Export and replacement commands can reach it from every Perform view, including with all panes closed. Keep editor-specific structural conflicts with their existing action and intent. Opening a different view must leave a pending draft available. Cancel or a failed save preserves the draft and the initiating context. [Project resolution dialog](../../frontend/src/components/clipArranger/DraftResolutionDialog.tsx) · [Resolution rules](../../frontend/src/lib/clipArranger/draftResolution.ts)

Use the existing workspace generation when New, Load or Import successfully replaces a performance, including loading the same ID twice. Preserve state on cancellation, failure and first save. After delete, Undo or Redo, revalidate remembered IDs, paths and passes. Fall back to the surviving parent or an empty selection without opening a dock or launching anything. New layout memory is session-only for this release. Cross-reload preferences remain an open product decision. [Generation tests](../../frontend/src/store/performanceWorkspaceGeneration.test.ts)

## 3. Build the bounded shell and shared controls

**Implemented in the application preview on 18 November 2026.** The real clip and legacy arrangers share a bounded shell and transport. Browser verification covered the desktop split, the single-pane editor, the Inspector drawer, real 200% zoom and changing panes during native playback. [Implementation record and replay](milestone-3-workspace-shell.md)

1. Constrain the **Perform** branch of the application shell to the available dynamic viewport, including its navigation, toolbar and status. Give the working row and columns shrinkable minimum sizes. Assign scrolling to the timeline, active detail, Inspector and mixer bank. Check which element actually scrolls with real content mounted.
2. Use one main column for the overview, horizontal divider and lower dock. Place the Inspector in a second column on the right spanning both panes. Closing the Inspector gives the width back. Closing Editor or Keyboard removes the entire dock and divider. A short song retains normal row heights and a usable empty timeline with **Add track**. **Fit tracks** changes display density only.
3. Give the divider pointer capture, visible focus, separator semantics and current/min/max values. Up/Down move 10 CSS pixels, Shift changes the increment to one, and Home/End reach the limits. Escape, pointer cancellation, lost capture, blur and a layout change during a drag restore the previous preferred height. Clamp the rendered height after resize and retain the chosen height for larger windows. Keep React editor instances stable through the gesture. [Divider rules](layout-and-interaction-spec.md#draggable-divider)
4. On narrow or short windows, show one working pane with an explicit return to the overview. Open the Inspector as a right-edge drawer. Focus its close control on explicit opening and return focus to its trigger on Close or Escape. Store the drawer and desktop sidebar preferences separately. Test the study's provisional 700 px width, 600 px height and 180 px/60% split limits against actual controls before fixing breakpoints.
5. Expose the existing performance identity, project/library actions, **Save performance**, help and instrument engine control in the shared shell. Keep one set of song transport commands, immediately above the timeline in Arrange and reachable during Live, Mix and expanded editing. Keep MIDI source, runtime failures and access to diagnostics visible. Bring over the existing import, conflict, export and delete flows with their keyboard focus behavior.

**Prove the shell** with the editor closed, expanded, resized and replaced by Keyboard. Measure the left edge of track names and top of the ruler before and after each change. Assert that the outer page fits, the closed dock reserves zero height and controls remain reachable at 200% browser zoom. The mock checker supplies scenarios and expected geometry. Run corresponding checks against the React application. [Preview checker](orch-study-preview-check.mjs)

## 4. Move Arrange and its editors

**Implemented in the optional application preview.** Arrange opens the selected clip occurrence or legacy pad below the timeline and exposes its properties in the right-hand Inspector. [Milestone 4 implementation and replay](milestone-4-arrange.md)

- Split the current clip composition into the overview, right-side properties, dock content and shared coordination. Keep the timeline's viewport measurement, sticky track headers, horizontal ruler synchronization and visible-range rendering. Use the existing musical units for precise seek, loop extent, playhead and end position. Carry over temporary lane Mute/Solo, Undo/Redo, section edits, clip Once/Loop, offsets, transposition and repetitions. Bound automation curves remain editable against their occurrences. [Timeline](../../frontend/src/components/clipArranger/ClipArranger.tsx) · [Transport](../../frontend/src/components/clipArranger/ClipTransport.tsx)
- Separate **select** from **open**. A single selection updates the Inspector and an already-open compatible editor. Double-click or a keyboard-accessible Open action reveals the correct dock. On load, retain compact lanes, the existing selection or loop fallback, and the closed editor. From an empty timeline, preserve **Add track**, the first clip and pattern, instrument assignment, and access to a playable instrument when the rack is empty.
- Reuse the existing single-device rendering path for melodic, drummer, Score, controller and arpeggiator editors. Keep the breadcrumb, scope, dirty state, **Play edit** and scoped Save together. Reuse the structural editor, local/all-linked scope, conflict handling, and definition relationships for usage counts. A local variation must leave siblings untouched. A linked save must update every affected use. Change labels using the real target and count, including the single-use case. [Editing scope](layout-and-interaction-spec.md#editing-scope-saving-and-audition) · [Structure editor](../../frontend/src/components/clipArranger/StructureEditor.tsx)
- Route legacy projects without a clip arrangement through the existing multitrack arranger and device operations inside the same shell. Preserve the explicit conversion, backup and incompatibility feedback where currently offered. Opening a view must never convert a performance. Exercise both the legacy project and a stored clip arrangement under the supported flag configurations. [Legacy arranger](../../frontend/src/components/MultitrackArranger.tsx) · [Compatibility reference](../redesign-arranger/legacy-arranger-reference.md)

**Prove the edit target.** Loop a chorus, select a nested occurrence, edit a local variation and leave it dirty. Edit a Live pad on the same device, then return. Verify both payloads, repetition, selected step, zoom, scroll and scope. Save the variation and inspect a sibling. Repeat with a linked structural edit, an inline automation edit and Cancel during conflict resolution.

## 5. Move Live, keyboard and MIDI

Extract the device launcher from the existing device controls. Both the full launcher and compact launcher beside the narrow-screen keyboard must call the same device actions. Show device name, playback source, independent Play/Stop, editing pad, playing pad and any queued pad. Use audible runtime markers for playing/queued feedback. Keep the existing device-specific launch boundaries, including Score and arpeggiator behavior. Pad selection while stopped or under Arrangement targets editing. An eligible running Manual device queues the launch.

Keep the keyboard mounted under its piano-roll identity while selecting a launch device or pad. The pad click updates the launcher and status. **Edit** opens the pad editor explicitly. Preserve the selected keyboard destination, octave, velocity, chord settings, MIDI channels and manual controller gestures. Releasing a key, closing the keyboard, leaving its view or losing focus sends the appropriate owned note-offs. Returning restores controls without replaying notes. [Piano keyboard](../../frontend/src/components/sequencer/PianoRollKeyboard.tsx) · [MIDI routing](../../frontend/src/hooks/useMidiControllerRouting.ts) · [Score launch behavior](../../documentation/performance/score_sequencers.md)

Map each Live editor action to what it actually writes. Use **Save pad N** for a pad-scoped draft commit, **Apply** for an existing reusable workspace definition, and explicit preset labels for preset operations. Some direct pad changes already take effect during playback. Preserve their live-edit timing. Where there is no existing pad commit, keep the edit live and surface its performance save status. Introducing deferred editing there would require a separate musical behavior decision. [Pattern workspace](../../frontend/src/components/sequencer/PatternWorkspace.tsx) · [Live edits](../../documentation/performance/live_status_and_safety_controls.md#editing-during-playback)

**Prove the launch.** Hold an Autochord, queue a second and then a third pad, and observe the actual device boundary. Confirm that the keyboard target and sounding chord survive each launch and that exit releases each held note once. Repeat on a phone-sized viewport with the compact launcher, and seek or stop the song while an independently started Manual device is running.

## 6. Move Mix, rack, routing and instrument settings

1. Expose Mixer, Rack and Routing as Mix subviews. Render instrument and return strips in a horizontally scrollable bank. Keep the existing `$master` strip pinned on the right and the stereo `$output` meter below bank and Master. Show destination, live gain, pan, sends, Mute/Solo and insert Bypass. Subscribe only visible meters and restore the latest readings on entry. [Mixer runtime](../../frontend/src/lib/mixerRuntime.ts) · [Routing guide](../../documentation/performance/audio_mixer_and_routing.md)
2. Use the compact rack for selection and the full rack for topology. Selecting a strip changes the Inspector target and leaves a closed dock closed. **Manage rack**, **Instrument controls**, **Samples** and **Routing** open their named destination. Preserve rack ordering, assignment, routing matrix, exact channel mapping, validation, feedback diagnostics and repair actions. Keep topology locks and explicit stop-to-edit. Opening routing must leave the engine running.
3. Bind settings, controller groups, CC mappings and sample maps to rack **instance** IDs. Preserve control types, exact values, defaults and update-mode indicators. Offer **Samples** only for a capable instance. Preserve uploads, validation, selected note and routed preview. Closing Samples ends its preview. Use the existing Instrument Design navigation and isolated draft audition when editing a patch graph. [Instance controls](../../frontend/src/components/sequencer/PerformanceControllerRack.tsx) · [Sample map editor](../../frontend/src/components/sequencer/SamplePlayerRack.tsx)

**Prove the signal path.** Run a routed source and a direct source together. Mute Master and verify that the direct signal remains audible and visible on Audio Output. Mute the direct strip and verify silence after any tails. Scroll the bank while both meters stay visible. Load two rack instances using the same patch, give the same note different samples, and confirm that selecting, previewing or editing one always addresses the intended instance.
